# UX 再設計：遊び方を「ラウンド」に一本化する

2026-10-11 時点の設計メモ。現状の「問題を解く」と「連続チャレンジ」の 2 本立てをやめ、
GeoGuessr 型の「1 ラウンド = 5 問、合計提出回数を競う」を唯一の遊び方にする。

## 1. 背景と問題

現状のトップページには「問題を解く」と「連続チャレンジ」の 2 つの入口がある。しかし両者の中核ループ
（問題を読む → 書く → 提出 → 判定）は完全に同じで、違いは次の 5 点だけである。

- ランダムに 5 問を出す
- 開始時にモードと残機を固定する
- 模範解答と履歴を隠す
- 合計提出回数を出す
- Wordle 風の共有文を出す

これを別ページ・別ナビ・別ストレージ・`PlayPage` 内の多数の分岐で実装しているため、プレイヤーには
「どちらで遊べばいいのか」が分かりにくく、コードも二重になっている。
自由プレイ側にも `recommend()` と「次の問題へ」があり、実質的に連続プレイは両方に存在する。

初回のプレイヤーが最初の提出に到達するまでに、現状は判断が 2 回必要（カードを選ぶ、問題を選ぶ）。

## 2. 設計原則

1. **遊び方は 1 つ**。「ラウンド」が唯一の単位。1 問だけ遊ぶのはその特殊ケース。
2. **開いたら即 1 問**。トップの主ボタンは 1 つで、押すとエディタが開く。
3. **問題一覧は二次導線**。記録の閲覧と、特定の問題のやり直しの場所に下げる。
4. **難易度や制約は「モード」ではなく「ラウンド開始前の設定」**。別ゲームにしない。
5. **出題の選び方（固定・ランダム・日替わり）はコースの種類**であって、遊び方の種類ではない。

## 3. GeoGuessr との対応

| GeoGuessr | OneShot Rust |
| --- | --- |
| 1 ゲーム = 5 ラウンド | 1 ラウンド = 5 問 |
| ラウンドごとの得点と合計点 | 問題ごとの提出回数と合計提出回数 |
| ラウンド間の結果画面と「Next round」 | 問題ごとの結果ダイアログと「次の問題へ」 |
| ゲーム終了のサマリーと共有 | スコアカードと共有文 |
| 「Play again」 | 「もう 1 ラウンド」 |
| マップ | コース（難易度別） |
| Move / Pan / Zoom 制限、時間制限 | 診断表示モード、残機 |
| Daily Challenge | 今日のコース（将来） |
| 地点の一覧は存在しない | 問題一覧は記録用に格下げ |

GeoGuessr から真似しない点：マップの種類が多すぎて選ぶ段階で迷う。コースは最初は少数に絞る。

## 4. ゲーム構造

### ラウンド

- 1 ラウンドは 5 問。問題はコースから選ぶ。
- スコアは合計提出回数。完璧は「問題数と同じ回数」（5 問なら 5）。「合計 7、完璧まで +2」のように表示する。
- 途中で離脱してもラウンドは保存され、次回は続きから再開する。
- 完走するとスコアカードを表示し、共有文を出し、「もう 1 ラウンド」へ誘導する。
- 現在の `Challenge` のデータ構造（`entries`、`totalSubmissions`、`challengeShareText`）はそのまま
  スコアカードとして流用する。

### コース

- コースは**難易度のみ**で分ける。3 段階で、コースは難易度ティアと 1 対 1。
  データは `problem.toml` の `difficulty = 1 | 2 | 3`、表示名は i18n で Beginner / Intermediate / Advanced（日本語は 初級 / 中級 / 上級）。
  整数なら並び順が自明で、将来 4 段階目を足すのも容易。
- コース名に題材（所有権、ライフタイムなど）は**出さない**。理由は次の 3 点。
  - 題材名は診断の答えそのもの。LSP なしでコンパイラと向き合うこのゲームでは「どこが問題かを見抜く」が
    中核スキルで、題材を先に言うと一番面白い工程を飛ばすことになる。
  - 問題 README は concepts を「作者向けのメモ。ネタバレになるのでプレイヤーには表示しない」と定めており、
    PR #12 で concept タグを隠している。コース名に出すのはその決定を裏口から覆す。
  - 1 問が複数の概念にまたがるのが普通なので、題材別にすると所属が揺れ、問題作りに逆方向の制約がかかる。
    難易度は 1 次元なので、ずれても「少し難しめ」で済む。
- 題材は解き終わった後の解説（editorial）で明かす。現状どおり。
- コース内の出題は**未解決優先のランダム**。同じコースを何度も遊べる。
- 問題数は増やせるので制約として考えない。コースごとの問題数は十分に確保する。

### スコアと Par の廃止

- **Par は廃止する**。理由：
  - ゲーム名が OneShot なので目標は常に 1 回。問題ごとに「2 回が想定」と言うのは前提を薄める。
  - ラウンド合計には「問題数 = 完璧」という自然な基準があり、Par がなくても結果を解釈できる。
  - Par は作者の推測で、問題が増えるほど一貫性を保ちにくい。回数は事実。
- Par に依存する称号（Birdie、Eagle、Bogey など）は廃止。**「Hole in One」だけは 1 回クリアの意味で残す**。
- 共有文は Wordle の「3/6」と同じ要領で、判定の絵文字列と回数だけにする。
- 難易度の情報は**粗い難易度ティア**として問題ごとに残す（Par の置き換え）。コースへの割り当てに使う。
  問題が増えて実データが溜まれば、Lichess のパズルレーティングのようにプレイ結果から自動で決めることもできる。

### ルール（診断表示モード・残機）

- 診断表示モードと残機は**ラウンド開始時に固定**し、途中では変えられない。
  現在の「設定を変えると次の run から反映」より分かりやすく、チャレンジ実装がすでに持つ方式と一致する。
- コース難易度（問題の難しさ）と診断表示モード（コンパイラがどれだけ教えてくれるか）は別の軸。混ぜない。
- 両方を開始前に選ばせると組み合わせが多くて迷うので、**診断表示モードは既定を Standard にし、
  「詳細設定」に下げる**。残機も同様。

### 模範解答と履歴

- 模範解答は**解いた後または諦めた後に常に表示**する。ラウンド中だけ隠す理由は薄い。
- 提出履歴は常に見られる。

### 記録の見せ方

- run は診断表示モード別に保持するが、**モードは run の属性としてバッジで出すだけ**にする。
  モードごとのベストを別テーブルとして見せたり、モードで絞り込むチップを置いたりはしない。
- 問題の履歴ページは実行を新しい順に並べ、各行に「判定の絵文字列、回数、モードのバッジ、日時」を出す。
- 記録ページ（問題一覧）の「ベスト」列は、モードを問わず最少回数の run を 1 つ出し、モードのバッジを添える。
  同点なら難しいモード、さらに同点なら新しい方を採る。
- ラウンド履歴とスコアカードも同じ扱いで、モードは行ごとのバッジ。ラウンド内はモードが固定なので、
  ラウンド単位の比較はもともと同条件。
- 設定の既定モードは「次のラウンドの既定値」という意味だけになり、表示には影響しない。

## 5. 画面と導線

| 画面 | 内容 |
| --- | --- |
| トップ | ヒーローとデモは残してよい。主ボタンは 1 つ：「ラウンドを始める」または「続きから」。初回は 1 クリックで 1 問目のエディタに入る。 |
| ラウンド開始前 | コース（難易度）を選ぶ。詳細設定として診断表示モードと残機。初回は既定（Beginner、Standard、残機なし）で即開始できる。固定の導入コースは用意しない。 |
| プレイ中 | 現在の `PlayView`。ヘッダに「3 / 5」。提出、諦める。 |
| 問題ごとの結果 | 「判定の絵文字列と回数」「次の問題へ」（最後の問題では「スコアカードへ」）「模範解答を見る」の 3 要素だけ。共有、コピー、履歴は置かない。 |
| スコアカード（ラウンド終了） | 各問題の回数、合計、完璧との差、モードのバッジ。共有文と画像はここで出す。「もう 1 ラウンド」。 |
| 問題一覧 / 記録 | ヘッダの二次導線。各問題のベスト記録（モードのバッジ付き）、解いた/未解決、ラウンド履歴。特定の問題をクリックすると**練習**として単独でやり直せる。練習はその問題の履歴とベストに残るが、ラウンドは作らない。問題単位の共有画像は履歴ページから出せる。 |
| 設定 | 言語、エディタ設定。診断表示モードと残機の既定値。 |

## 6. 将来の拡張（同じ UI の上に足す）

- **今日のコース**：日付をシードにした固定ラウンド。全員が同じ 5 問を解く。トップで「今日のラウンド」を
  1 回遊び、完走後に「もう 1 ラウンド」でランダムに続く。入口は 1 つのまま日次の習慣化を得られる（Lichess の構成）。
- **無限ストリーム**：ラウンドの区切り（5 問）を外せば Lichess Puzzles / Codewars Train 型になる。
  ラウンド型から外す移行は簡単だが逆は難しいので、先にラウンド型で作る。
- **データ由来の難易度**：プレイ結果から難易度ティアを自動調整する。

## 7. 既存コードへの影響

削除・統合：

- `web/src/ui/ChallengePage.tsx`（Start / Summary / ChallengePage）を、ラウンド開始前画面とスコアカードに作り替える。
- `web/src/ui/PlayPage.tsx` の `ChallengeContext` 分岐を畳む。常にラウンド内なので「自由プレイか否か」の分岐は不要。
- `web/src/ui/HomePage.tsx` のカード 2 枚を主ボタン 1 つにする。`recommend()` は「続きから / 新規」の判定だけに縮める。
- `web/src/core/route.ts` の `challenge` ルートと `play` ルートを統合する。
- `web/src/core/solution.ts` の `inChallenge → hidden` を削除する。
- `web/src/storage/db.ts` の `draftKey` と `problemsInProgress` の challenge 分岐を整理する。
- ナビの「Challenge」項目を削除する（遊び方が 1 つになるため）。

Par 廃止：

- `problems/*/problem.toml` の `par` を難易度ティアに置き換え、`problems/README.md` を更新する。
- `web/src/core/scoring.ts` の `titleFor` を「Hole in One」判定だけにする。
- `web/src/ui/ParMeter.tsx` の目標マークを外し、回数のメーターにする。
- 問題一覧の並び順とコース割り当てを難易度ティアに切り替える。
- 共有文・共有画像から「(Par 2, Birdie)」を外す。
- i18n の `parTooltip`、`meterTooltip`、`challenge*` 系の文言を整理する。

流用：

- `web/src/core/challenge.ts` の `Challenge`、`recordRun`、`totalSubmissions`、`solvedCount`、`challengeShareText` は
  ラウンド / スコアカードとしてほぼそのまま使う。
- `FinishedDialog` の共有画像生成はスコアカードにも使う。

## 8. 決定事項（元は未決だったもの）

1. **問題ごとの結果ダイアログ**：「判定の絵文字列と回数」「次の問題へ」「模範解答を見る」の 3 要素だけ。
   共有、コピー、履歴はスコアカードと記録ページに移す。ラウンドが得点の単位なら共有の単位もラウンド。
   模範解答だけ残すのは、GeoGuessr がラウンド間で正解地点を見せるのと同じで、学びの機会をその場で与えるため。
2. **記録ページからの単独やり直し**：練習として扱い、ラウンドは作らない。提出は問題の履歴に残り、ベストは更新される。
   ラウンドは合計を競う場、記録ページは問題ごとのベストを競う場、という役割分担にする。
3. **難易度ティア**：3 段階、`difficulty = 1 | 2 | 3`、表示名は i18n。コースはティアと 1 対 1。
4. **固定導入コース**：用意しない。初回は Beginner コースを既定選択し、未解決優先のランダムで始める。
   固定コースはコースの種類を増やし、選定と更新の手間が継続的にかかる。
5. **モード別記録**：データは run ごとに保持し、モードは run の属性としてバッジで見せる。
   モード切替チップやモード別のベスト表は置かない。詳細は「記録の見せ方」。
